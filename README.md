# 鉄道運行シミュレータ

時刻表(ダイヤ)を入力として、鉄道の運行を詳細に再現するブラウザアプリケーション。
単なるアニメーションではなく、実際の運行計画が持つ構造 — **ダイヤ / 車両運用 / 入庫・出庫 /
構内ダイヤ / 検査周期** — をデータモデルとして持ち、整合性を機械的に検証し、時間軸に沿って
可視化する。

テストケースとして **東急大井町線の平日1日フルダイヤ**を同梱している。

```bash
npm ci
npm run dev          # http://localhost:5173
```

---

## できること

| | |
|---|---|
| **路線ビュー** | 駅の全番線と車庫の全留置線を描いた**配線略図**の上を、列車が時刻表どおりに走る。列車は位置そのものに打たれた点で、番線への出入りは分岐器のリードをなぞる ── 消えることもワープすることもずれることもない。列車名・編成・待避/折返は重ならない行に配置される |
| **運行図表(スジ)** | 時刻 × 距離のダイヤグラム。追い抜きは線の交差、待避は水平線として一目でわかる。1つの運用を強調表示すると、その編成の1日がひとつながりの線になる。**上下線の一方だけ**を描くこともできる |
| **時刻表グリッド** | OuDia 風の編集画面。行=駅(着/発/番線)、列=列車。キーボードで高速入力できる |
| **運用エディタ** | 1運用=1編成の1日の仕業。列車の連鎖をタイムラインで表示し、連続性の破れをその場で指摘する |
| **構内ダイヤ** | 駅単位で 時刻 × 番線 の在線図。番線の二重使用が視覚的にわかり、ドラッグで再割付できる。**入換**(同じ編成が番線を移ったこと)は棒と棒を結ぶ線として描かれ、時間軸は拡大・平行移動できる |
| **編成・検査** | 編成ごとの積算キロ(**導出値**)と、列車検査・月検査・重要部検査・全般検査の期限 |
| **検証パネル** | 38 のルールで整合性を検査。クリックすると該当箇所へジャンプする |
| **詳細パネル** | 選択した列車の諸元に加えて**その列車の運用**を示し、運用画面を開く/運行図表で強調する の2つの見かたを提供する |

プロジェクトは JSON として import / export でき、作業中は IndexedDB に自動保存される。
サーバもデータベースも不要。

## 設計上の判断

実装を読む前に知っておくと理解が早い点を挙げる。

### 車庫は「駅」である

`Depot` は `kind: 'depot'` を持つ `Station` を指す。km 軸から少し外れた位置に置かれる。

この結果、**出庫・入庫の回送は普通の `Train`** になる。位置の補間も、番線の在線判定も、
運行図表の描画も、運用の連続性チェックも、回送に対して何も特別扱いせずに動く。
「車庫への出入り」という別系統のコードが一切存在しない。

路線ビューでも同じで、車庫の留置線は駅の番線とまったく同じ「レーン」として描かれる。
ただし**車庫の長さだけは縮尺どおりではない**。鷺沼車庫は 17 km の線区に対して 500 m
── 幅の 3% ── しかなく、そこに 10 本の留置線を扇形に描いても線の塊にしかならないため、
描画上の長さには下限を設けてある(`depotStubReach`)。km 軸で意図的に縮尺を崩している
唯一の場所で、遠方の長津田車両工場に上限を設けているのと同じ判断の裏返しである。
`placeTrain` は km をこの描画上のスタブに写すので、回送が車庫に着く**時刻**は
時刻表どおりのままになる。

### 列車は消えないしワープしない

路線ビューの列車位置は、**そのとき描かれている線路の上の点**として定義されている。

- 番線が走行レーンと違うとき、駅の両端に**分岐器のリード**が描かれる。列車はその
  リードを補間しながら移動するので、発車の瞬間にレーンが飛ぶことがない
- 車庫の入出庫も同じで、引上線 → 扇形の分岐 → 留置線 と、描かれた線をたどる
- 通過は「その脚に付いた注記」であって停車ではない。以前は通過前後6秒の間 km を駅に
  スナップしていたため、列車が駅まで飛んで12秒静止しまた飛ぶ、という挙動になっていた

**折り返しでも消えない。** 列車が終着に着いてから、同じ運用の次の列車が発車するまでの
間、車両はそこに立っている。この事実は運用(`Duty`)にしか書かれていないので、
`buildIndex` がそれを読んで `TrainTimeline.layover` に落とし、`trainRuntimeAt` は
`layover` フェーズを返す ── 「1列車の時刻表だけで位置が決まる」という性質は保たれる。
結果として、ひとつの編成は運用が終わるまで**常にちょうど1つ**のマーカーとして描かれる。
`stable` レグが引上線への入換を指示している場合は、レーン間を 90 秒かけて渡る。

### 列車は点、説明は別の行

**混雑をよけるために動かしてよいのは文字だけで、列車は動かさない。**

以前の路線ビューは 92×26 px の箱を列車の位置に置き、箱どうしが重なるときは
レーンに沿ってずらしていた。これは順序を保つ最小二乗解で、箱としては正しく並ぶ。
だが線区ビューが伝えたい唯一のことが「列車がどこにいるか」である以上、
**ずらしてよいものではなかった**。16本/時の線区では、ほぼ全部の箱が常にずれる。

いまは列車は位置そのものに打たれた小さな点で、種別色・回送は白抜き・待避中は
琥珀のリング、という「読まなくてもわかる情報」だけを担う。列車名と編成番号と
待避/折返は、16 px の行グリッドに詰めた**ラベル**として別に置かれる ──
自分の列車のすぐ下の行を第一希望に、空いている最寄りの行へ。3行以内に空きが
なければラベルは**落とす**。駅名バンドとまったく同じ判断で(`StationLabelPlacer`
を共用している)、点は残るので位置の情報は失われず、拡大すれば文字は戻ってくる。

ラベルの**書体・級数・色は急行停車駅の駅名と同一**にしてある。ここは読むための
文字だからで、種別色で染めるとその条件を満たせない ── 暗い地に対して読める赤は
もう赤ではない。種別色は点と、ラベル左端の色帯に移した。

### ホームは「一番狭い駅間」から決める

番線の平らな部分がホームとして読める部分で、その長さは実際の有効長ではなく
**一番狭い駅間の 0.35 倍**から決めている。130 m のホームを 17 km の線区に
縮尺どおり描けば 0.5 px にしかならず、ホームとして読めない。0.35 なら
隣り合う駅ブロックが決してぶつからず、駅間の走行区間も残る。

### 引上線は駅の「外」に出す

引上線は駅を貫く線路ではなく、ホームの先に突き出した行き止まりである。
溝の口の2本は**梶が谷寄り**にあり、大井町にはそもそも無い(その事実が線区の
本数上限を決めている)。どちら側かはドキュメントに書かれていないので、
**その駅が近いほうの線区の端**を向く、という規則で導いている ── 終端駅では
必ず正しく、途中駅でも最善の推定になる。`stubSide` に書いてある。

### 停車パターンはテンプレートにすぎない

`Train` は自分自身の `stops[]` を実体として持つ。`StopPattern` は列車を生成するときの
雛形であり、シミュレーション時には読まれない。`Train.patternId` は由来を記録するだけ。

実際のダイヤは例外だらけで、パターンを編集した瞬間に人間が入力した数百の時刻が
黙って書き換わる、という事態は避けなければならない。

### 時刻は「営業日の 00:00 からの秒数」で、86400 を超えてよい

`formatTime(88200)` は `24:30` を返す。日本のダイヤは深夜帯を翌日ではなく同一営業日の
連続した時刻として書き、実際に日付をまたいで走る列車が存在するため、24時で折り返して
しまうと表示も順序比較も壊れる。ドメイン層に `Date` は一切登場しない。

### シミュレーションは (project, t) の純粋関数

列車の位置はその列車自身の時刻表だけで決まるので、逐次シミュレーションする必要がない。

- 任意時刻へのシークが `O(稼働中の列車数)`。スジをドラッグしてスクラブできる
- フレーム時間のばらつきが累積してずれることがない
- 再生中に編集しても、次のフレームで新しいインデックスを読むだけ。差分適用のコードが要らない

唯一の状態を持つオブジェクトはクロックだけ。

なお駅間の補間には**台形速度プロファイル**を使っている(等速の線形補間ではない)。
ホームで急停止して等速で走り出す列車は、見た瞬間に嘘だとわかってしまう。

### 走行キロは保存値ではなく導出値

`Formation.odometerKm` は `odometerAsOf` 時点の基準値で、現在値は
「基準値 + それ以降に充当された運用の距離」として毎回計算される。

シミュレーションがこれを書き換えてしまうと、読み込んで再生して保存しただけで
ドキュメントが変わってしまい、undo/redo が成立しなくなる。
**エンジンはドキュメントを一切変更しない。**

## 東急大井町線の再現について

`src/seed/oimachi/facts.ts` に、調査で確認した事実をコメント付きで記述している。
特に設計を決定づけた3点:

**待避設備は2箇所しかない。** 旗の台(島式2面4線、3・6番線が待避線、両方向・終日)と、
上野毛(島式1面3線、**上り方向のみ**)。大岡山と自由が丘は4線あるが他線との共用なので
待避できない。この制約が線区の運転本数の上限をそのまま決めている。

なお同梱ダイヤでは、**追い抜きは142本すべて旗の台**で行われ、上野毛の待避線は
使っていない。上野毛は設備としてはモデル化してあり(`canBeOvertaken` は上り側のみ true)、
生成器は不正な待避駅を拒否するのでそこに待避を置くこともできるが、
16本/時では1サイクルにつき旗の台の1回で足りてしまうため出番がない。
現実の朝ラッシュは上野毛でも追い抜くので、これは下の「朝ラッシュ」の項と同じ理由による
再現できていない点である。

**各駅停車は「緑」と「青」の2種類あり、違いは経路である。**
二子玉川〜溝の口は方向別複々線(内側=大井町線、外側=田園都市線)で、
二子新地・高津には**大井町線側にホームがない**。したがって青各停は二子玉川で
外側線へ転線する。停車パターンのフラグではなく物理的な経路の違いなので、
`StationTrack.hasPlatform` としてモデル化している。

**大井町は頭端式1面2線**で引上線がなく、ホーム上で折り返す。線区最大の隘路。

### 同梱ダイヤの規模

```
列車 546 (営業 478 / 回送 68)   下り 273 / 上り 273
種別 緑各停 201 / 急行 142 / 青各停 135 / 回送 68
運用 34 (5両 29, 7両 5)          編成 23 (5両 17, 7両 6)   同時運用最大 20
待避停車 142 / 緩急接続 142 (すべて旗の台)
運転時間帯 04:19 〜 25:33
検証 エラー 0 / 警告 13 / 情報 2
```

終端の在線ピークは **大井町 2/2線・溝の口 5/6線・鷺沼 3/4本** で、いずれも容量内。

### 忠実度についての注意

公表時刻表の各列車の実時刻は入手していない。同梱のダイヤは、確認済みの**構造的事実**
— 日中15分サイクル(急行1+各停3)、16本/時、待避駅、急行7両/各停5両、鷺沼での入出庫 —
から**再構成**したものである。「実在ダイヤの逐語コピー」ではなく「実在ダイヤと同じ構造・
同じ制約を満たすダイヤ」を生成している。`src/seed/` は決定論的な生成器で、`Date.now()` も
`Math.random()` も使わないため、実行するたびに同一の出力になる。

**朝ラッシュ・夕ラッシュは 16本/時、オフピークは 12本/時。** 現実の大井町線はもっと
詰まっているので、ここは再現しきれていない。理由は 大井町 が頭端式1面2線であること:
上り列車はすべてそこで折り返して下り列車になるため、**ピーク時の本数は方向間で対称**に
なる(保存則)。2線で折り返し240秒+余裕を捌くと理論上の上限は約24本/時だが、
急行が旗の台で各停を追い抜くために必要な 245秒以上の間隔を空けると、2線での
塗り分けが18本/時で破綻する。18本/時のパターンを実際に組んで検証した結果、急行が
2本前の各停に溝の口までに 60秒 まで詰めてしまい、大井町〜溝の口 に2つめの下り待避線が
ない以上どうにもならないことを確認した(`src/seed/oimachi/service.ts` に記録)。

**16本/時で成立するダイヤのほうが、20本/時で成立しないダイヤより価値がある**と判断して
16/16 を採用している。検証ルールを緩めたり、線路配置の事実を書き換えたりはしていない。

**オフピークの 12本/時 は 急行1+各停2 で、現実の 急行1+各停3 ではない。** 1:3 の
12本/時 は1周期20分を要し、20分周期と、30分の準備バンドが使う15分周期とでは
青各停と緑各停の比が食い違う。青と緑は二子玉川〜溝の口で別の線路を走り(二子新地・
高津にホームがあるのは田園都市線側だけで、そこに停まるのは青だけ)、運用を融通できない
(`DutyNode.routing`)。バンド境界ごとに緑が1本余って大井町の2線に置き場がなくなり、
ラッシュのど真ん中を全線回送で入庫させるしかなくなる — その筋は引けない。
条件を満たす20分グリッド 78,359 通りを総当たりで確かめた結果を
`src/seed/oimachi/service.ts` の冒頭に記録してある。

## 構成

```
src/
  domain/      エンティティ型・時刻演算・Zod スキーマ・参照整合性   ← React も DOM も知らない純粋TS
  engine/      インデックス構築・位置導出・待避検出・在線・検査投影・クロック
  validation/  38 のルール(rules/ 配下)と実行エンジン
  seed/        東急大井町線の生成器(パターンDSL → 列車 → 番線 → 運用 → 入出庫)
  store/       コマンド・Immer パッチによる undo/redo・永続化
  render/      Canvas 2D の路線ビューと運行図表、SVG の構内ダイヤ
  ui/          シェルと全エディタ画面
e2e/           Playwright。testids.ts は src/ui と共有する契約
```

依存の向きは `domain ← engine ← validation ← seed` で、`render` は `ui` を決して import しない。

### テストの考え方

**Canvas は Playwright から中身が見えない。** そこで各キャンバスビューは、描画したものを
そのまま反映した**非表示の DOM リスト**(`.visually-hidden`)を 4Hz で publish している。
E2E はピクセルではなくこれを検証する。安定して読みやすく、失敗時の出力が意味を持ち、
おまけにアクセシビリティ上の代替表現にもなる。60Hz の描画パスは DOM に一切触れない。

加えて `window.__render.digest(view)` が描画済み要素のスクリーン座標を返すので、
座標変換そのものを end-to-end で検証できる。

E2E は `?e2e=1` で決定論モードに入る — rAF クロックを起動せず、`window.__sim.setTime()` が
同期的に1フレーム描画する。自動保存の復元は無効。ID は連番。CSS トランジションは無効。
**スイート中に `waitForTimeout` は1箇所も存在しない。**

検証ルールのテストは1ルールにつき2件 — 発火するフィクスチャと、しないフィクスチャ。
どちらも `src/testing/toyProject.ts` の4駅の小さな路線から出発し、1箇所だけ壊す。

## v1 の範囲外

- **構内の進路・分岐器の競合**。v1 の構内ダイヤは「1列車が1番線を
  `[着 − 進入余裕, 発 + 開通余裕]` の間だけ占有する」という単純なモデル。
  実際の連動装置の再現は別の問題であり、意図的に含めていない。路線ビューが描く
  分岐器のリードも同じで、**線がつながっていることを示すだけ**で競合は表現しない
- **車庫の留置線の割付**。生成器は車庫では**空いている線から順に**埋めるので、
  夜間滞泊の19編成は10本の留置線に散る(以前は駅の既定番線という概念が車庫にも
  適用され、出庫はすべて留置10番線、入庫はすべて留置1番線 ── 1本の線に19編成が
  重なって描かれていた)。ただし在線は入出庫の瞬間しか予約しないため、いまでも
  1本の留置線に複数の編成が同時に載ることがあり、路線ビューはそれをそのまま
  描く(`6104F +2` のように)。車庫の在線容量を1線1編成として解く問題は、
  線区の番線割付とは別の解法が要る
- 複数路線(`Line` 型は存在するので追加は加算的にできる)
- 乗務員運用
- 遅延の伝播(`TimeOverlay` という接合点だけ用意してある)
